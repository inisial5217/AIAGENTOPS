## 1. Ringkasan Eksekutif

Fase 3 mengimplementasikan infrastruktur keamanan identitas dan otorisasi kelas enterprise (Identity & Access Management / IAM) untuk platform CIFO:
- **Keycloak 24.0.5 OIDC Provider**: Berjalan live pada container Docker port 8180 dengan realm `cifo` terimpor otomatis saat startup. Menggunakan isolasi skema PostgreSQL `currentSchema=keycloak` di database `cifo_db` tanpa data tiruan (zero mock).
- **Stateless JWT Validation & In-Memory JWKS Cache**: Validasi tanda tangan kriptografi RS256 token JWT dengan thread-safe caching JWKS publik key (TTL 1 jam), menghasilkan latensi verifikasi sub-10 milidetik tanpa membebani server Keycloak di setiap permintaan HTTP.
- **Role-Based Access Control (RBAC)**: Penegakan hierarki hak akses tiga tingkat (`admin` > `devops` > `viewer`) dengan respons standar RFC 7807 Problem Details (`application/problem+json`) dan pencegahan akses yang ketat.
- **Auto User Synchronization**: Pengguna yang pertama kali login melalui Keycloak otomatis disinkronkan dan di-upsert ke tabel PostgreSQL `users` (`id`, `email`, `name`, `role`, `keycloak_id`, `is_active`).
- **Audit Logging Kepatuhan Keamanan**: Setiap event otentikasi (`login` sukses/gagal, `logout`) dan pelanggaran otorisasi (`access_denied`) dicatat secara append-only ke tabel PostgreSQL `audit_log` lengkap dengan aktor, IP, user-agent, dan detail JSON.
- **Token Revocation & Redis Blacklist**: Logout mencatat token JWT ke Redis 7 dengan waktu kedaluwarsa dinamis (`time.Until(exp)`), memblokir seketika penggunaan ulang token sebelum masa berlakunya habis.
- **Integrasi Frontend Next.js**: Axios interceptor otomatis menginjeksi token Bearer, Zustand store mengelola state otentikasi, dan komponen interaktif `AuthControl` memungkinkan pengujian langsung hak akses di antarmuka web.

## 3. Detail Implementasi Arsitektural

### 3.1. Keycloak Container & Realm `cifo`
- **Container**: Image resmi `quay.io/keycloak/keycloak:24.0.5`, container name `cifo-keycloak`.
- **Database Backend**: PostgreSQL 16 container `cifo-postgres` menggunakan JDBC URL:
  `jdbc:postgresql://postgres:5432/cifo_db?currentSchema=keycloak`
  Isolasi skema `keycloak` menjaga integritas tabel aplikasi pada skema `public`.
- **Clients**:
  - `cifo-frontend`: Public client (standard flow & password grant untuk CLI/pengujian), redirect URIs `http://localhost:3000/*` dan `http://127.0.0.1:3000/*`, Web origins `*`.
  - `cifo-backend`: Bearer-only client untuk validasi resource API.
- **Roles Realm**:
  - `admin`: Akses penuh konfigurasi sistem, user management, dan settings.
  - `devops`: Akses operasional Docker, Kubernetes, ArgoCD, dan interaksi AIOps.
  - `viewer`: Akses observabilitas baca-saja (read-only).
- **Akun Pengguna Bawaan (Pre-configured Users)**:
  - `admin@cifo.local` (Password: `admin123`, Role: `admin`)
  - `devops@cifo.local` (Password: `devops123`, Role: `devops`)
  - `viewer@cifo.local` (Password: `viewer123`, Role: `viewer`)

### 3.2. Stateless JWT Validation & In-Memory JWKS Cache
Validasi token dilakukan secara terdesentralisasi tanpa network round-trip ke Keycloak pada setiap request:
```go
// JWKSCache menyimpan RSA public key hasil parsing JWKS
type JWKSCache struct {
    sync.RWMutex
    keys      map[string]*rsa.PublicKey
    expiresAt time.Time
    ttl       time.Duration
    jwksURL   string
    client    *http.Client
}
```
1. Handler menerima header `Authorization: Bearer <token>`.
2. Middleware mengecek keberadaan token di Redis blacklist (`jwt:blacklist:<sha256>`). Jika ditemukan, langsung kembalikan HTTP 401 ("token has been revoked").
3. JWT di-parse dan diverifikasi tanda tangan RS256-nya menggunakan public key dari cache JWKS.
4. Jika `kid` tidak ada di cache atau TTL (1 jam) kedaluwarsa, cache otomatis me-refresh daftar kunci publik dari endpoint OIDC certs Keycloak.

### 3.3. Penegakan Otorisasi (RBAC) & Hierarki Peran
Hierarki peran didefinisikan secara numerik:
```go
var roleHierarchy = map[string]int{
    "admin":  3,
    "devops": 2,
    "viewer": 1,
}
```
Setiap rute yang dilindungi memanggil middleware `RequireRole(authService, minRole)`:
- `admin` dapat mengakses rute bertingkat `admin`, `devops`, dan `viewer`.
- `devops` dapat mengakses rute bertingkat `devops` dan `viewer`, tetapi ditolak pada rute `admin`.
- `viewer` hanya dapat mengakses rute bertingkat `viewer`, dan diblokir dengan HTTP 403 Forbidden pada rute `devops` dan `admin`.
- Setiap insiden penolakan (403) memicu pencatatan audit log otomatis dengan aksi `access_denied`.

### 3.4. Format Error Standar RFC 7807
Respons kesalahan otentikasi dan otorisasi menggunakan Content-Type `application/problem+json`:
```json
{
  "title": "Forbidden",
  "status": 403,
  "detail": "Insufficient permissions: role 'admin' required",
  "instance": "/api/v1/admin/users"
}
```

### 3.5. Auto Synchronization ke PostgreSQL
Saat token JWT yang valid diterima:
1. `AuthService.SyncUser` mengekstrak `sub` (Keycloak User UUID), `email`, `name`, dan `roles`.
2. Menentukan role utama pengguna berdasarkan prioritas peran.
3. Menjalankan `UserRepository.UpsertKeycloakUser`:
   - Jika pengguna dengan `keycloak_id` atau `email` sudah ada, data nama dan role diperbarui (`updated_at = NOW()`).
   - Jika belum ada, record baru disisipkan secara atomik dengan ID UUID baru dan `is_active = true`.

### 3.6. Audit Logging Kepatuhan Keamanan
Semua mutasi keamanan disimpan append-only di tabel `audit_log`:
- Event `login` (sukses / gagal)
- Event `logout` (sukses)
- Event `access_denied` (pelanggaran otorisasi RBAC)
