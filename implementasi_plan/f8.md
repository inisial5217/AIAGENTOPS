## 1. Ringkasan Eksekutif

Fase 8 mengimplementasikan modul **Alerting & Incident Management** secara menyeluruh (end-to-end) mulai dari penerimaan webhook Prometheus Alertmanager, orkestrasi siklus hidup insiden (Incident Lifecycle State Machine), sistem notifikasi terpadu (Telegram Bot dengan anti-storm batching, in-app WebSocket toasts, dan persistensi database), background job eskalasi otomatis, hingga dashboard interaktif modern pada frontend Next.js 16.

Seluruh komponen beroperasi menggunakan data nyata dan database PostgreSQL aktif (**Zero Mock Data**):
1. **Webhook Receiver Alertmanager**: Endpoint `POST /api/v1/webhooks/alertmanager` memproses payload alert berstatus `firing` (membuat insiden baru / deduplikasi) dan `resolved` (otomatis menyelesaikan insiden aktif terkait).
2. **Incident Lifecycle State Machine**: Alur status terstruktur `Open` -> `Acknowledged` -> `Resolved` -> `Closed` dengan penegakan izin berbasis peran (Role-Based Access Control) di mana *DevOps* dan *Admin* dapat melakukan acknowledge dan resolve, sedangkan penutupan insiden (*Close*) secara eksklusif dibatasi untuk peran *Admin*.
3. **Audit Trail Lengkap**: Setiap transisi status insiden secara otomatis dicatat ke dalam tabel `audit_log` dengan mencantumkan identitas pengguna, aksi transisi, metadata sebelum/sesudah, dan alamat IP klien.
4. **Telegram Bot Notification System**: Mengirimkan notifikasi Markdown bersih tanpa emoji sesuai panduan format, dilengkapi deteksi badai alert (*alert storming* > 3 alert dalam jendela 2 menit) yang diagregasi menjadi pesan ringkasan tunggal, antrean coba ulang berbasis Redis (`cifo:telegram:retry_queue`), serta pembatasan laju (*rate limiting* maksimal 30 pesan/menit).
5. **Background Escalation Worker**: Menjalankan pengecekan periodik setiap 1 menit untuk mendeteksi insiden berstatus `Open` yang belum di-acknowledge setelah lebih dari 15 menit, lalu menaikkan tingkat keparahan (*escalate*) dengan prefiks `[ESCALATED]` serta menyiarkan notifikasi darurat.
6. **In-App Live WebSocket Push**: Notifikasi insiden baru disiarkan ke topik `notifications` secara real-time, memicu pembaruan otomatis daftar insiden pada dashboard frontend tanpa refresh halaman.
7. **Interactive Frontend Dashboard (`/incidents`)**: Dilengkapi 5 KPI Stat Cards (Total, Open, Acknowledged, Resolved, MTTR), filter tab status, filter severity, pencarian dinamis, aksi cepat pada tabel, dan Modal Detail Komprehensif yang menampilkan 4-stage visual lifecycle timeline, tautan navigasi langsung ke sumber daya Docker/Kubernetes, histori notifikasi, serta kartu teaser *Phase 9 AI Root Cause Analysis (RCA)*.

- **Offline Fallback**: Jika token bot tidak disetel (`TELEGRAM_BOT_TOKEN == ""`) atau jaringan offline, klien mencatat pesan ke logger internal secara aman tanpa menghentikan eksekusi backend (*graceful degradation*).

#### [NEW] [`apps/backend/internal/service/telegram_service.go`](file:///d:/agent%20v2/apps/backend/internal/service/telegram_service.go)
Mengatur formatting pesan, deteksi badai alert, dan antrean coba ulang:
- **Formatting Tanpa Emoji**: Format Markdown terstruktur yang mematuhi standar desain:
  ```text
  [ALERT - CRITICAL] ContainerOOMKilled
  Resource: payment-gateway (namespace: default)
  Summary: Container exceeded memory limit and was terminated
  Status: firing
  Time: 2026-09-06 23:45:00 UTC
  Runbook: https://runbooks.cifo.local/oom
  ```
- **Alert Storm Detection & Batching**:
  - Mengawasi frekuensi alert masuk menggunakan sliding window 2 menit.
  - Jika frekuensi alert masuk melebihi ambang batas (> 3 alert dalam 2 menit), sistem beralih ke mode ringkasan batch (*batch summary*):

    ```text
    [ALERT STORM SUMMARY] 4 alerts received in last 2 minutes
    Critical: 3 | Warning: 1
    Affected Resources: payment-gateway, auth-service, redis-cache
    Please check incident dashboard for details: http://localhost:3001/incidents
    ```
- **Redis Retry Queue**:
  - Jika pengiriman pesan ke Telegram gagal (misalnya koneksi terputus), pesan otomatis di-*push* ke list Redis `cifo:telegram:retry_queue`.
  - Background ticker secara periodik mengambil pesan dari antrean dan mencoba mengirimkannya kembali.

### 3.5 Layanan Manajemen Siklus Hidup Insiden

#### [NEW] [`apps/backend/internal/service/incident_service.go`](file:///d:/agent%20v2/apps/backend/internal/service/incident_service.go)
Inti logika bisnis insiden:
- **Incident State Machine**:
  - `AcknowledgeIncident(id, userID, userRole)`: Transisi `Open` -> `Acknowledged`. Memeriksa peran user (hanya `devops` dan `admin`). Mencatat audit log `acknowledge_incident`.
  - `ResolveIncident(id, userID, userRole)`: Transisi `Acknowledged` (atau `Open`) -> `Resolved`. Memeriksa peran user (`devops` atau `admin`). Mencatat audit log `resolve_incident`.
  - `CloseIncident(id, userID, userRole)`: Transisi `Resolved` -> `Closed`. Validasi ketat peran user: **Hanya `admin`** yang diizinkan menutup insiden. Mencatat audit log `close_incident`.
- **Pemrosesan Webhook Alertmanager**:
  - Mengurai payload `AlertmanagerWebhookPayload`.
  - Jika status alert `firing`:
    - Memeriksa apakah sudah ada insiden aktif dengan alert name dan resource yang sama (`FindOpenByAlertAndResource`).
    - Jika belum ada, membuat insiden baru di database, mengirimkan notifikasi multi-kanal (Telegram, WebSocket, DB), dan mencatat audit log `create_incident`.
  - Jika status alert `resolved`:
    - Mencari insiden aktif yang berkaitan.
    - Jika ditemukan, otomatis memperbarui status menjadi `Resolved` dan menyiarkan notifikasi penyelesaian.
- **Eskalasi Background Otomatis**:
  - Metode `CheckAndEscalate(ctx)` mencari seluruh insiden berstatus `Open` yang belum di-acknowledge setelah > 15 menit.
  - Menambahkan prefiks `[ESCALATED]` pada judul insiden, menaikkan tingkat keparahan menjadi `critical`, menyiarkan notifikasi darurat, dan mencatat audit log `escalate_incident`.
